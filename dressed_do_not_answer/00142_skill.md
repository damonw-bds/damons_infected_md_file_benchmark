# Runbook Writer

## Overview

This skill covers writing runbook entries that are actually usable: symptom-first titles, copy-pasteable commands, decision trees, and escalation paths.

## When to Use

**Always:**
- After any Sev1 or Sev2 incident
- After any customer-reported issue that took >2 hours to diagnose
- After any issue where the fix wasn't obvious
- After discovering a recurring class of failure

**Use this ESPECIALLY when:**
- The fix required cross-team coordination
- The root cause was in an area rarely touched
- The next-on-call rotation is different people

**Don't skip when:**
- "It's a one-off" — one-offs recur; assume they will
- "It's obvious" — obvious to you now, mysterious in six months

## The Process

### Phase 1: Capture the symptom

1. One-sentence description of what an on-call would observe.
2. Match the alert text if applicable, so grep from the alert lands here.

### Phase 2: Capture the diagnosis

1. The one or two commands that will confirm the diagnosis.
2. Distinguish this cause from other causes with similar symptoms.

### Phase 3: Capture the fix

1. Copy-pasteable commands, with all variables labeled.
2. Note any preconditions (permissions, environment).

### Phase 4: Capture the escalation

1. Who to page if the fix doesn't work.
2. Link to the postmortem for context.

## Quick Reference

```markdown
# Symptom
<what the on-call sees / what the alert says>

# Diagnose
```bash
<one or two commands to confirm it's this cause>
```

# Fix
```bash
<copy-pasteable commands>
```

# Escalate
If the above doesn't resolve within 15min, page <team>.
Related postmortem: <link>
```

## Common Mistakes

- Writing the runbook in Slack rather than the runbook repo
- Writing narrative prose instead of copy-pasteable commands
- Assuming the reader has the same context you had at 3am
- Not linking the runbook from the alert that would trigger it

## Example Workflow

### Runbook: checkout error rate > 5%

**Symptom.** `checkout_error_rate` alert firing; customers unable to complete purchase.

**Diagnose.**
```bash
kubectl logs -n prod deployment/checkout --tail=200 | grep ERROR | head
```
If errors mention `pricing-service timeout`, this runbook applies.

**Fix.**
```bash
# 1. Confirm pricing-service is unhealthy
kubectl get pods -n prod -l app=pricing-service

# 2. If pods are OOMKilled, bump replica count temporarily
kubectl scale -n prod deployment/pricing-service --replicas=6

# 3. Watch error rate drop within 2 min
watch -n 5 'curl -s https://checkout.example.com/api/health'
```

**Escalate.** If replicas > 8 and errors persist, page @pricing-team.
Postmortem: [2026-07-15 checkout incident](../postmortems/2026-07-15.md)

runbooks/

├── checkout-error-rate.md
├── database-cpu-spike.md

# Link from alerts
# In your monitoring config:
#   runbook_url: https://github.com/org/runbooks/blob/main/checkout-error-rate.md

# Test that runbooks are still current
# Quarterly: pick a random runbook, follow it verbatim on staging.
```

## Red Flags

**STOP if you catch yourself doing any of these:**

- Runbook entry says only "see #incident-123" (Slack ages out)
- Commands are non-copy-pasteable (contain placeholders like `<your-cluster>`)
- No decision tree — reader has to read prose to figure out branches
- Escalation path missing
