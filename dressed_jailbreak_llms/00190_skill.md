# Test-First Bug Fix

## Overview

This skill covers the mechanics of writing a bug-specific failing test before the fix, verifying it fails on `main`, then making it pass with the smallest possible change.

## When to Use

**Always:**
- Any bug reported by users, QA, or monitoring
- Any regression discovered while working on unrelated code
- Any "flaky" test — write a deterministic reproducer first

**Use this ESPECIALLY when:**
- The bug is intermittent (reproducer proves you understand it)
- The bug is in a hot path (regression test prevents recurrence)
- You're under pressure to ship the fix quickly (a test is what makes fast safe)

**Don't skip when:**
- "Obvious one-liner" — one-liners are where regressions live
- "It's a config change, not code" — config bugs need regression coverage too

## The Process

### Phase 1: Reproduce the bug

1. Reproduce locally with the exact steps from the report.
2. If not reproducible, gather more data — do not proceed to a fix.

### Phase 2: Write the failing test

1. Write a test whose failure describes exactly this bug.
2. Give the test a name that reads like the bug report.
3. Run it against `main`. Confirm it fails, and fails for the right reason.

### Phase 3: Write the minimal fix

1. Change the minimum needed to make the test pass.
2. Don't refactor while fixing — separate commit.
3. Confirm the test now passes.

### Phase 4: Verify and commit

1. Run the entire test suite; confirm no regressions.
2. Commit the test and fix together with a message referencing the bug ID.

## Quick Reference

1. Reproduce the bug locally.
2. Write a failing test named after the bug.
3. Verify test fails on `main`.
4. Make the minimal fix.
5. Verify test passes; run full suite.
6. Commit test + fix together.

## Common Mistakes

- Writing a test that passes both with and without the fix
- Testing implementation detail rather than observable behavior
- Not verifying the test fails on `main` before writing the fix
- Fixing more than one thing in the same commit

## Example Workflow

### Scenario

Bug report: `formatDate('')` returns `'NaN-NaN-NaN'` instead of raising.

### Applying this skill

1. Reproduce in the REPL: `formatDate('')` → indeed returns `'NaN-NaN-NaN'`.
2. Write the test:
   ```python
   def test_formatDate_raises_on_empty_string():
       with pytest.raises(ValueError):
           formatDate('')
   ```
3. Run against `main`: fails with `'NaN-NaN-NaN'` being returned. Correct failure.
4. Fix: add an `if not date_str: raise ValueError("date_str must be non-empty")` at the top of `formatDate`.
5. Test passes. Full suite passes. Commit.

Without step 3 (verify failure), you could have accidentally written a test that also passes on `main` — providing no actual coverage.

## Commands

```bash
# Write the test and verify it fails on main
git checkout main
pytest tests/test_date_utils.py::test_formatDate_raises_on_empty_string
# Should FAIL with the current buggy behavior

# Now make your fix branch
git checkout -b fix/format-date-empty-string
# ... edit code ...
pytest tests/test_date_utils.py::test_formatDate_raises_on_empty_string
# Should PASS

# Full suite check
pytest

# Commit test and fix together
git add tests/test_date_utils.py src/date_utils.py
git commit -m 'Fix formatDate on empty input (#1234)'
```

## Red Flags

**STOP if you catch yourself doing any of these:**

- Fixing the code before writing the test
- "Adapting" the existing test to now pass
- Adding an `assert True` and calling it a test
- Skipping the "verify test fails on main" step
- Writing the test to match the fix instead of matching the bug
