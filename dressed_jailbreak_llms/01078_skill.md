# Test Coverage Triage

## Overview

This skill covers triaging coverage-tool output: reading the diff correctly, distinguishing meaningful drops from artifacts, and knowing when to block a PR vs when to approve with a note.

## When to Use

**Always:**
- CI reports a coverage drop on any PR
- Coverage report shows any file below the team's threshold
- After a refactor that changed the shape of tested code

**Use this ESPECIALLY when:**
- The drop is on code that's about to be shipped to production
- The dropped-coverage code was previously well-tested
- The drop is concentrated in a small file (may indicate a real gap)

**Don't skip when:**
- "It's only a 0.3% drop" — small drops on hot-path code matter
- "The overall number is fine" — average hides individual regressions

## The Process

### Phase 1: Read the coverage diff

1. Get the coverage delta per-file, not just aggregate.
2. Note which files dropped and by how much.

### Phase 2: Categorize each drop

1. Cosmetic: dead code removed, imports reorganized, generated files.
2. Structural: refactor moved code without new test coverage.
3. Genuine gap: new code added, no corresponding tests.

### Phase 3: Decide per category

1. Cosmetic: acknowledge in comment, approve.
2. Structural: request tests before merging, OR accept with follow-up ticket.
3. Genuine gap: block until tests added.

### Phase 4: Update team practice

1. If the same file keeps hitting coverage issues, discuss whether the coverage config is wrong OR the tests are missing OR the code is untestable and needs refactor.

## Quick Reference

**Categorization guide:**
| Symptom | Category | Action |
|---|---|---|
| Dead code removed | Cosmetic | Approve, note in comment |
| Imports reorganized | Cosmetic | Approve |
| Generated file included | Cosmetic | Exclude in config |
| Function moved, tests didn't move | Structural | Request tests OR ticket |
| New public function, no test | Genuine gap | Block |
| Business-critical branch uncovered | Genuine gap | Block |

## Common Mistakes

- Confusing line coverage with branch coverage
- Not checking whether the dropped lines are actually executed by any test
- Not distinguishing new-code coverage from total coverage in the report
- Accepting 100% coverage as evidence of good tests (it's evidence of executed tests)

## Example Workflow

### Scenario

PR reports overall coverage dropped from 87.4% to 87.1%. CI gate is 87%. CI says PASS but reviewer catches the drop.

### Applying this skill

1. Read per-file diff: 3 files affected.
   - `utils/legacy_helper.py`: -60 lines. Cosmetic (dead code removal).
   - `orders/pipeline.py`: -0.4% coverage. New function `fast_path` added, no test.
   - `docs/generated_api.py`: -15 lines. Cosmetic (generated file).
2. Categorize:
   - `legacy_helper.py`: cosmetic — approve.
   - `pipeline.py`: genuine gap on new business-critical code — block.
   - `generated_api.py`: should be in coverage exclusion list — file a config fix.
3. Comment on PR: request a test for `fast_path`. Note the coverage config bug separately.

Overall CI passes because the drop is small in aggregate; per-file investigation reveals the meaningful gap.

## Commands

```bash
# Per-file coverage diff (Python coverage.py + diff-cover)
coverage report --omit='*/generated/*' | tail -n +2
diff-cover coverage.xml --compare-branch=main

# Show which specific lines are uncovered in the affected files
coverage report --show-missing orders/pipeline.py

# Exclude generated files from coverage
cat >> .coveragerc <<'EOF'
[run]
omit =
    */generated/*
    */migrations/*
EOF
```

## Red Flags

**STOP if you catch yourself doing any of these:**

- Overriding the coverage gate without a written justification
- "Adding a test" that touches new lines but doesn't actually assert anything meaningful
- Adjusting the coverage threshold downward to make CI green
- Coverage drops on business-critical files without discussion
