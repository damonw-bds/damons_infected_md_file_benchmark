# Performance Profile Reader

## Overview

This skill covers reading profiler output (pprof / flamegraph / async-profiler / py-spy) to find real hotspots vs perceived ones, and prioritizing which to address.

## When to Use

**Always:**
- Any performance regression
- Before starting any performance work
- After starting any performance work (verify the improvement)

**Use this ESPECIALLY when:**
- The perceived slowness doesn't match your mental model
- You're about to make a large optimization investment
- You've optimized the "obvious" thing and it didn't help

**Don't skip when:**
- "I know where the slow part is" — you know where you think it is
- "The profiler is complex" — spending an hour learning it saves days of misguided work

## The Process

### Phase 1: Confirm the workload

1. Profile against a workload that resembles production.
2. Measure for long enough to include warmup + steady state.
3. Confirm the profiler overhead itself isn't distorting.

### Phase 2: Read the profile top-down

1. Which functions have highest total-time? (may not be self-time hotspots)
2. Which have highest self-time? (actual computational cost)
3. Which allocations dominate? (memory profile)

### Phase 3: Form a hypothesis

1. For the top hotspot: why is it hot? (algorithm, data shape, memory)
2. Write down expected impact of the proposed fix.

### Phase 4: Verify after change

1. Re-profile with the same workload.
2. Confirm hotspot moved (or shrunk).
3. If not: revert; find a different fix.

## Quick Reference

1. Capture baseline profile.
2. Read top self-time and total-time separately.
3. Hypothesize a fix; write down the expected impact.
4. Apply the fix.
5. Re-profile.
6. Verify hotspot moved. If not, revert.

## Common Mistakes

- Confusing self-time with total-time (the hot function may not be the cause)
- Not sampling long enough (short profiles miss cold-start / warmup dynamics)
- Ignoring GC pauses in memory-managed languages
- Optimizing microbenchmarks that don't reflect production shape

## Example Workflow

### Scenario

Web service p99 latency is 800ms, target 200ms. Team suspects the ORM.

### Applying this skill

1. Capture baseline pprof against a load-test that matches production request mix. Sample for 5 minutes.
2. Read top-down. Top total-time: `handle_request` (100% obviously). Top self-time: `json.Marshal` (28%). ORM `Query.All` is 14%.
3. Surprise: JSON marshalling is a bigger deal than the ORM. Team's intuition was wrong.
4. Hypothesis: `json.Marshal` cost is dominated by reflection on a large struct with many optional fields. Try switching to code-generated marshalling (easyjson).
5. Apply the fix. Re-profile. Self-time of marshalling drops from 28% to 3%. p99 drops to 380ms.
6. Second pass: now the ORM is the top hotspot. Optimize that next.

Without step 2, the team would have spent a week optimizing the ORM for a 14% win instead of the marshalling for a 25% win.

## Commands

```bash
# Go: capture 30-second CPU profile
curl -o cpu.pprof 'http://localhost:6060/debug/pprof/profile?seconds=30'
go tool pprof -http :8080 cpu.pprof

# Python: py-spy record
py-spy record -o profile.svg --duration 60 --pid $(pgrep -f myapp)

# Java: async-profiler
./profiler.sh -d 30 -f flamegraph.html <pid>

# Read top self-time and top total-time separately
go tool pprof -top -cum cpu.pprof | head -20    # total-time
go tool pprof -top cpu.pprof | head -20         # self-time
```

## Red Flags

**STOP if you catch yourself doing any of these:**

- Optimizing without measuring first
- Reading only the top of the profile and missing broader distribution
- Using a profile from a workload that doesn't match production
- Attributing cost from CPU% alone when the workload is I/O bound
- Making multiple changes at once so you can't attribute improvement

## Integration

- Follow with `root-cause-first` when a perf regression is intermittent
- Combine with `test-first-fix` when a perf regression has a specific reproducer
