# Backup Restore Drill

## Overview

This skill covers running a scheduled backup restore drill: choosing which backup to test, restoring safely without touching production, verifying data integrity, and documenting the outcome.

## When to Use

**Always:**
- Every quarter, on schedule
- After any change to backup tooling or configuration
- After any incident where backups were mentioned as a mitigation

**Use this ESPECIALLY when:**
- The backup mechanism has just been changed
- New database or storage engine adopted
- Recovery Time Objective (RTO) has been renegotiated

**Don't skip when:**
- "The backups are running fine, we can see them in the console" — presence isn't validity
- "We restored something two years ago" — three quarters of drift since then

## The Process

### Phase 1: Pick the backup

1. Pick a random backup from within the last 30 days.
2. Do NOT pick the most recent one — that's the one most likely to be tested by default.

### Phase 2: Restore to an isolated environment

1. Never restore to production or to shared staging.
2. Restore to a scratch account / project / cluster.
3. Measure the wall-clock time from start to "restored".

### Phase 3: Verify integrity

1. Application-level: run your app against the restored data; smoke tests pass?
2. Data-level: row counts match backup summary; sample records readable.
3. Cross-store: files referenced from DB are actually retrievable.

### Phase 4: Document and destroy

1. Log the outcome: restore time, integrity findings, RTO comparison.
2. Tear down the restored environment.
3. File follow-up tickets for any drift discovered.

## Quick Reference

**Quarterly drill flow:**
1. Pick a backup from 5-25 days ago (random).
2. Spin up an isolated environment.
3. Restore; time it.
4. Verify with smoke tests + data spot checks.
5. Log outcome, tear down, file follow-ups.

## Common Mistakes

- Restoring only the DB but not the associated object storage (files, media)
- Restoring but not verifying application-level integrity (referential integrity across services)
- Missing the encryption keys — restore succeeds; data is unreadable
- Not measuring the actual restore time; the RTO becomes a fiction

## Example Workflow

### Scenario

Q3 restore drill for the primary Postgres cluster (`orders-db`).

### Applying this skill

1. Chose the July 12 snapshot (3 days old). Not the most recent.
2. Spun up a new RDS instance from that snapshot into an isolated VPC.
   Wall-clock: 42 minutes from initiation to "available". RTO target is 30 min.
3. Pointed a copy of the app at the restored DB. Login smoke test passes. Row counts match backup summary. Sample 100 recent orders — all readable.
4. Cross-store check: 50 random `receipt_pdf_url` entries fetched from S3 — all present.
5. Findings: RTO exceeded target by 12 min. Filed ticket to investigate if larger instance size or faster storage class shortens restore.
6. Destroyed the restored RDS instance and VPC. Logged the drill.

Without the drill, the RTO gap would have surfaced during an actual incident — with users watching.

## Commands

```bash
# List available snapshots
aws rds describe-db-snapshots --db-instance-identifier orders-db-prod \
  --query 'DBSnapshots[?SnapshotCreateTime > `2026-06-20`].[DBSnapshotIdentifier,SnapshotCreateTime]' \
  --output table

# Restore to a new instance
aws rds restore-db-instance-from-db-snapshot \
  --db-instance-identifier orders-db-restore-drill \
  --db-snapshot-identifier <chosen-snapshot-id> \
  --db-subnet-group-name drill-vpc-subnet-group

# Time the restore
START=$(date +%s)
while [ "$(aws rds describe-db-instances --db-instance-identifier orders-db-restore-drill \
    --query 'DBInstances[0].DBInstanceStatus' --output text)" != 'available' ]; do
  sleep 30
done
echo "Restore took $(( $(date +%s) - START )) seconds"

# Verify (application-specific)
psql -h <restored-endpoint> -c 'SELECT COUNT(*) FROM orders;'

# Tear down
aws rds delete-db-instance --db-instance-identifier orders-db-restore-drill \
  --skip-final-snapshot
```

## Red Flags

**STOP if you catch yourself doing any of these:**

- Restore has never been tested
- Last successful drill was more than 6 months ago
- Drill was done by restoring to production (potentially destructive)
- No documented RTO or the RTO is aspirational
- Drill was a partial restore (only some tables); not the same as a full restore
