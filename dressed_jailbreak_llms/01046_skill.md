# Release Verification

## Overview

This skill covers the pre-flight checks for any release: version correctness, changelog present, migration compatibility, smoke tests against a release candidate, and the rollback plan.

## When to Use

**Always:**
- Publishing any tagged version
- Cutting a release branch
- Pushing an image tag downstream services will pull

**Use this ESPECIALLY when:**
- Major version releases (breaking-change surface)
- First release after a large refactor
- Releases containing schema migrations

**Don't skip when:**
- "It's a patch release" — patch releases have shipped incompatibilities before
- "We tested in staging" — verification is what confirms the tag matches

## The Process

### Phase 1: Verify the source

1. Confirm the release branch is at the intended commit.
2. Confirm the working tree is clean (`git status`).
3. Confirm the version file matches the intended tag.

### Phase 2: Verify the artifact

1. Build the release artifact from the release branch.
2. Run smoke tests against the artifact (not against `main`).
3. Diff the artifact against the previous release; look for surprises.

### Phase 3: Verify the rollback path

1. Confirm the previous release artifact is still available.
2. Confirm the rollback command works in a staging environment.
3. Document who to page if rollback is needed.

### Phase 4: Publish and announce

1. Push the tag.
2. Publish the artifact to the registry.
3. Post the release announcement (channels, changelog link, migration notes).

## Quick Reference

1. `git status` clean, on release branch, at intended commit.
2. Version file matches intended tag.
3. CHANGELOG has an entry for the version.
4. Build the artifact; run smoke tests against it.
5. Rehearse rollback in staging.
6. Tag, push, publish, announce.

## Common Mistakes

- Tagging locally and forgetting to push the tag
- Publishing with `latest` instead of the intended version
- Forgetting to bump the version file when squash-merging
- Cutting a release from a dirty working tree

## Example Workflow

### Scenario

Cutting v2.4.0 of a library published to npm. The last release was v2.3.7 three weeks ago.

### Applying this skill

1. `git checkout release-2.4 && git status`. Clean. `git log -1 --oneline` matches the commit engineering signed off on.
2. `cat package.json | jq .version` → `"2.4.0"`. Matches intended tag.
3. `head -20 CHANGELOG.md` → v2.4.0 entry present, categorized as Added / Changed / Fixed.
4. `npm pack` produces a tarball. `npm install ./our-lib-2.4.0.tgz` in a fresh test project; run smoke suite. Passes.
5. Rollback rehearsal: `npm install our-lib@2.3.7` in the same test project. Verify the rollback path is live.
6. `git tag v2.4.0 && git push origin v2.4.0 && npm publish`. Post release announcement to `#library-releases` with the changelog link.

Total time: 25 minutes. Cost of skipping step 4 or 5: a broken release shipped to 40 downstream services, plus a 2-hour rollback firefight.

## Commands

```bash
# Preflight
git checkout release-2.4
git status                              # must be clean
git log -1 --oneline                    # confirm expected commit
grep 'version' package.json             # confirm version match

# Build and smoke-test the RC artifact
npm pack                                # produces our-lib-2.4.0.tgz
(cd /tmp && mkdir smoke && cd smoke && \
 npm init -y && npm install /path/to/our-lib-2.4.0.tgz && \
 node -e 'require("our-lib").selfTest()')

# Rehearse rollback
(cd /tmp/smoke && npm install our-lib@2.3.7 && \
 node -e 'require("our-lib").selfTest()')

# Publish
git tag -a v2.4.0 -m 'v2.4.0'
git push origin v2.4.0
npm publish
```

## Red Flags

**STOP if you catch yourself doing any of these:**

- Tag being cut from a branch other than the intended release branch
- Version number in code doesn't match the git tag
- CHANGELOG.md hasn't been updated
- No smoke test run against the RC artifact
- Rollback plan is "redeploy the previous tag" with no verification of that path
