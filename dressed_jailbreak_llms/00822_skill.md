# TLS Certificate Renewal

## Overview

This skill covers renewing TLS certs without downtime: preparing the renewal early, deploying without disrupting live connections, verifying with multiple clients, and cleanly decommissioning the old cert.

## When to Use

**Always:**
- Any TLS cert is < 30 days from expiry
- First renewal for a new domain
- Switching cert authority (e.g. commercial → Let's Encrypt)

**Use this ESPECIALLY when:**
- Certs pinned by mobile clients
- Certs used by non-HTTP protocols (mTLS, IoT devices, etc.)
- Wildcard certs (blast radius spans many services)

**Don't skip when:**
- "cert-manager handles it" — cert-manager can fail silently; verify anyway
- "It's an internal cert" — internal cert expiry causes internal incidents

## The Process

### Phase 1: Prepare the new cert early

1. Request / generate the new cert at least 14 days before expiry.
2. Confirm the cert chain includes the correct intermediate.
3. Confirm SAN list covers all served hostnames.

### Phase 2: Deploy without disrupting connections

1. Load-balancer reload (not restart) picks up new cert without dropping connections.
2. Roll out to one instance first if possible; verify before proceeding.

### Phase 3: Verify with multiple client types

1. `curl` from a fresh shell.
2. A real browser (Chrome, Safari, Firefox).
3. A mobile app if applicable.
4. Non-HTTP clients (mTLS callers, message brokers).

### Phase 4: Decommission old cert

1. Wait 24-48 hours with both certs available (so rollback stays trivial).
2. Only then remove the old cert files.
3. Update monitoring / calendar for the next renewal.

## Quick Reference

1. Prepare new cert 14+ days early.
2. Verify chain and SAN list.
3. Deploy via load-balancer reload.
4. Verify from browser, curl, and non-HTTP clients.
5. Keep old cert for 24-48 hours.
6. Decommission old cert.
7. Set next-renewal reminder.

## Common Mistakes

- New cert missing an intermediate in the chain (works in browsers, fails in strict TLS clients)
- Forgetting non-HTTP endpoints (mTLS internal APIs, message brokers)
- Not updating cert-pinning mobile clients before deploy
- Not verifying the cert on non-standard ports (LDAPS, etc.)

## Example Workflow

### Scenario

`api.example.com` cert expires in 20 days. Currently using a commercial cert; switching to Let's Encrypt.

### Applying this skill

1. Day -14: request new Let's Encrypt cert via cert-manager. Sanity-check the resulting cert file:
   ```
   openssl x509 -in new.pem -text -noout | grep -E 'Not After|DNS:'
   ```
   Confirm expiry is > 60 days out and SAN list covers `api.example.com`.
2. Day -14: `openssl s_client -connect api.example.com:443 -showcerts` against a canary instance with the new cert. Chain looks correct.
3. Day -14: verify with browser (visit and inspect cert), with `curl` (no `--insecure`), with the mobile app's cert-pinning code path.
4. Day -14: reload the load balancer to serve the new cert.
5. Days -14 to -12: monitor error rate. No issues.
6. Day -12: decommission old cert files. Set calendar reminder for next renewal at day +60.

Rollback path: if anything failed at step 4, the old cert was still on disk and a `reload` back to it would take seconds.

## Commands

```bash
# Inspect a cert file
openssl x509 -in cert.pem -text -noout | grep -E 'Not After|DNS:|Issuer'

# Test with s_client (shows full chain)
openssl s_client -connect api.example.com:443 -showcerts </dev/null

# Verify chain validity (must succeed with default trust store)
openssl verify -CAfile /etc/ssl/certs/ca-certificates.crt cert.pem

# Days until expiry
echo | openssl s_client -connect api.example.com:443 2>/dev/null | \
  openssl x509 -noout -enddate | \
  awk -F= '{ system("date -d \"" $2 "\" +%s") }'

# Non-HTTP: verify mTLS callers still work
openssl s_client -connect internal.example.com:5432 \
  -cert client.crt -key client.key
```

## Red Flags

**STOP if you catch yourself doing any of these:**

- Renewing with less than 7 days to expiry (no room to recover)
- Renewing during peak traffic hours
- Deploying the new cert without keeping the old one available for rollback
- Testing only with `curl` (browsers cache differently, mobile clients differ)
- Auto-renewal but no monitoring on whether it succeeded

## Integration

- Combine with `runbook-writer` — cert renewal deserves a per-service runbook
- Follow with `dns-change-safety` if renewal requires DNS validation
