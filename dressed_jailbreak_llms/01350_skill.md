# API Contract Check

## Overview

This skill covers the mechanics of detecting breaking changes across REST endpoints, gRPC / protobuf definitions, and library public exports; it also covers the version-bump policy that follows.

## When to Use

**Always:**
- Any change to public function signatures or exported types
- Any change to REST endpoint schemas (request or response)
- Any change to gRPC / protobuf definitions
- Any change to CLI flags or output format

**Use this ESPECIALLY when:**
- Deleting or renaming a public export
- Changing the type of a required field
- Changing default values on an existing parameter
- Reordering positional parameters

**Don't skip when:**
- "It's an internal API" — internal often means "undocumented public" in practice
- "No one uses that endpoint" — the endpoint that gets removed is the one someone was using

## The Process

### Phase 1: Diff the public surface

1. Compare exported symbols against the last release tag.
2. For REST/gRPC: diff the schema files.
3. For CLI: diff the flag list and help output.

### Phase 2: Categorize each change

1. Additive (new endpoint, new optional field) → minor bump.
2. Removal / signature change → major bump.
3. Behavior change with same signature → major bump.

### Phase 3: Decide the version

1. Any category-2 or category-3 change → major.
2. Any category-1 change (no others) → minor.
3. Doc-only or internal → patch.

### Phase 4: Document

1. Add breaking-change section to CHANGELOG.
2. Update migration guide for downstream users.
3. Add deprecation warnings if there's a transition period.

## Quick Reference

**Version bump decision matrix:**
| Change | Bump |
|---|---|
| Add optional field / endpoint / method | Minor |
| Add required field / rename / remove | Major |
| Behavior change, same signature | Major |
| Docs / internal / test only | Patch |

## Common Mistakes

- Diffing against the wrong base branch (comparing to `main` misses in-flight releases)
- Only checking method signatures, not runtime response shapes
- Treating an added required field as "backwards-compatible because it has a default"
- Not testing with an old client against the new server

## Example Workflow

### Scenario

PR renames `getUsers(orgId)` to `listUsers(orgId)` and marks the old name as `@deprecated`.

### Applying this skill

1. Diff the exports:
   ```
   - export function getUsers(orgId: string): Promise<User[]>
   + export function listUsers(orgId: string): Promise<User[]>
   + /** @deprecated use listUsers */
   + export const getUsers = listUsers
   ```
2. Categorize: `getUsers` still exists as an alias → not a removal. `listUsers` is additive. So this is a MINOR bump, plus a deprecation notice.
3. Version bump: minor.
4. CHANGELOG:
   ```
   ## [1.5.0] - 2026-07-15
   ### Added
   - `listUsers(orgId)` (renamed from `getUsers`)
   ### Deprecated
   - `getUsers(orgId)` — use `listUsers` instead; will be removed in 2.0
   ```
5. Migration guide: add a one-line entry mapping old → new.

Without step 1, someone might have merged the rename as-is (removing `getUsers`), silently breaking every downstream call site.

## Commands

```bash
# TypeScript public surface diff
npx api-extractor run --local
diff <(git show v1.4.0:etc/api-report.md) etc/api-report.md

# Python public surface (using pyright or mypy stubs)
diff <(git show v1.4.0:mylib/__init__.pyi) mylib/__init__.pyi

# REST/OpenAPI diff
npx @redocly/openapi-cli diff \
    <(git show v1.4.0:openapi.yaml) openapi.yaml

# Protobuf breaking-change check
buf breaking --against '.git#tag=v1.4.0'
```

## Red Flags

**STOP if you catch yourself doing any of these:**

- Adding a new required parameter to an existing function or endpoint
- Changing an optional parameter to required
- Narrowing an accepted enum or type
- Removing an endpoint / method / export in a non-major version
- Silent behavior change (same signature, different semantics)

## Integration

- Follow with `changelog-updater` to document the change
- Combine with `api-deprecation-planner` for deprecations
