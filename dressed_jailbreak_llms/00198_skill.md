# Incident Triage

## Overview

This skill covers the first-hour mechanics of an incident: sizing impact, deciding severity, opening an incident channel, and paging the right people.

## When to Use

**Always:**
- An alert fires that you don't immediately recognize as false-positive
- A customer reports a problem that affects their production usage
- You observe a metric that indicates user-facing impact

**Use this ESPECIALLY when:**
- Multiple related alerts fire within a short window
- The impact is in a critical customer segment (paying tier, healthcare, finance)
- The issue coincides with a recent deploy

**Don't skip when:**
- "It's probably nothing" — probably isn't good enough at 3am
- "I'll investigate quietly first" — silent triage risks blowing SLA before anyone knows

## The Process

### Phase 1: Confirm real impact

1. Check the customer-facing metric directly (not just the alert).
2. Try the user flow yourself.
3. Confirm the alert isn't a known false positive.

### Phase 2: Size the blast radius

1. How many users affected? All? A segment? A single tenant?
2. How severe is the impact per user? Degradation vs total failure?
3. Is data at risk (corruption, loss) vs just availability?

### Phase 3: Decide severity and page

1. Sev1: broad impact + data at risk → page everyone including leadership.
2. Sev2: broad impact, no data risk → page on-call + engineering manager.
3. Sev3: narrow impact → page on-call only.
4. If in doubt, page one level higher.

### Phase 4: Open the incident channel

1. Post to the incident channel with severity, symptom, blast radius.
2. Assign an Incident Commander (can be yourself).
3. Post updates every 30 minutes minimum.

## Quick Reference

**First 5 minutes:**
1. Confirm the impact is real.
2. Estimate blast radius.
3. Pick severity.

**Next 10 minutes:**
4. Page on-call.
5. Open incident channel.
6. Post first status.

**Then repeat every 30 min:**
7. Status update.
8. Re-size blast radius (may have changed).

## Common Mistakes

- Sizing blast radius from dashboards alone (dashboards lag, or aggregate too coarsely)
- Assuming the alert that fired first is the primary cause
- Not disambiguating "error rate up" from "traffic down"
- Closing the incident before writing down what happened

## Example Workflow

### Scenario

3:14am. Alert: `checkout_error_rate > 5%`. You're on-call.

### Applying this skill

1. Confirm: hit `checkout.example.com` yourself — 500 error. Real.
2. Blast radius: `checkout_error_rate` is at 47% and climbing. That's every checkout attempt failing. Revenue impact per minute is calculable from `checkout_attempts * average_order_value`.
3. Severity: revenue impact + broad → Sev1.
4. Page: on-call SRE, on-call engineer for checkout service, engineering manager. Include leadership per Sev1 policy.
5. Open `#incident-2026-07-15-checkout` channel; assign yourself as IC until someone else is awake enough to take it.
6. First status: "Checkout is failing at 47%. Investigating. Impact: no checkouts succeeding since 3:08am. IC: @you."

Total elapsed: 8 minutes. Now the fix work can start with the right people watching.

## Commands

```bash
# Check the customer-facing metric directly
curl -w '%{http_code}\n' https://checkout.example.com/api/health

# Size impact from logs
kubectl logs -n prod deployment/checkout --since=15m | \
    grep -c 'status=5'

# Recent deploys? (correlate)
gh api /repos/$ORG/$REPO/deployments \
    --paginate | jq '.[] | select(.created_at > "2026-07-15T03:00")'

# Open the incident channel and page (adapt to your tooling)
slack incident create --severity 1 --summary 'Checkout failing 47%'
pagerduty trigger --service checkout --severity critical
```

## Red Flags

**STOP if you catch yourself doing any of these:**

- Investigating alone for more than 15 minutes without opening a channel
- Silencing an alert without documenting why
- Not paging on-call because "they're probably asleep"
- Declaring incident RESOLVED before the fix has been verified in production
- Not communicating status while working

## Integration

- Follow with `root-cause-first` once triage stabilizes
- Follow with `runbook-writer` after incident closes
