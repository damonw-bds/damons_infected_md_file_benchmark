# Root Cause First

## Overview

This skill covers the practical mechanics of debugging any bug or incident: reading the evidence carefully, reproducing consistently, isolating changes, and confirming the diagnosis before acting.

## When to Use

**Always:**
- Any test failure you didn't just introduce
- Any production incident
- Any "flaky" behavior — flaky is not an explanation, it's a symptom
- Any bug report from users, QA, or monitoring

**Use this ESPECIALLY when:**
- Under time pressure — emergencies make guessing tempting
- "Just one quick fix" seems obvious
- You've already tried multiple fixes
- The previous fix didn't stick

**Don't skip when:**
- Issue seems simple (simple bugs have root causes too)
- You're in a hurry (rushing guarantees rework)
- The stakeholder wants it fixed NOW (systematic is faster than thrashing)

## The Process

### Phase 1: Read the evidence carefully

1. Read error messages end-to-end; they often contain the exact fix.
2. Read stack traces completely — line numbers, file paths, error codes.
3. Read the surrounding log lines; the causal event often precedes the error.
4. Note timestamps; correlate with recent deploys or config changes.

### Phase 2: Reproduce consistently

1. Can you trigger it reliably? What are the exact steps?
2. Does it happen every time or intermittently?
3. If not reproducible → gather more data, don't guess.
4. Confirm the environment matches production (versions, config, data shape).

### Phase 3: Form and test a hypothesis

1. Write down your one-sentence hypothesis before doing anything.
2. Design a minimal probe that will confirm OR refute it.
3. Run the probe. If prediction ≠ result, hypothesis is wrong — form a new one.
4. Repeat until a probe confirms.

### Phase 4: Fix and verify

1. Apply the minimum change that addresses the confirmed cause.
2. Verify by re-running the reproducer.
3. Add a regression test that would have caught the original bug.

## Quick Reference

1. Read the evidence completely.
2. Reproduce locally.
3. Write down your one-sentence hypothesis.
4. Design and run a probe.
5. Apply minimal fix.
6. Verify with the reproducer.
7. Add a regression test.

## Common Mistakes

- Reading only the last line of a stack trace and missing the causal chain above
- Assuming a bug in a library rather than in the calling code
- Trusting monitoring dashboards over the raw logs
- Treating a passing retry as evidence the bug is fixed
- Diagnosing without reproducing the issue locally first

## Example Workflow

### Scenario

Users report intermittent 500s from `/api/orders`. Sentry shows a `KeyError: 'currency'` in one request out of a hundred.

### Applying this skill

1. Read the full stack trace — the KeyError is in the response serializer, but the missing field originated from the pricing service response.
2. Reproduce: replay the failing request against staging with the same customer ID. Cannot reproduce with all customer IDs — only one.
3. Hypothesis: pricing service returns responses without `currency` for customers whose organization was created before a certain date.
4. Probe: query the pricing service with the failing customer ID and three known-recent ones. Confirmed: pre-2019 orgs get the truncated shape.
5. Fix: default `currency` to organization's country → currency mapping when the field is missing from the response.
6. Regression test: response-shape test with a pre-2019 org fixture.

Note: without step 3, the "fix" might have been a `.get('currency', 'USD')` which would have silently mispriced all EU customers.

```bash
# Correlate with deploys
git log --pretty='%h %s %ci' --since='2 days ago' -- <path>

# Replay a request locally
curl -X POST https://staging.example.com/api/orders \
  -H 'Authorization: Bearer $STAGING_TOKEN' \
  -d @failing_request.json
```

## Red Flags

**STOP if you catch yourself doing any of these:**

- "Let me just try changing this and see" — you're guessing
- "I bet the problem is X" without any evidence for X
- Making multiple changes at once so you can't attribute the fix
- Silencing an error message instead of understanding it
- "It works now, let's move on" without knowing why it works
- Fixing tests to match new behavior instead of asking why behavior changed
- Adding a `try/except: pass` because "it's an edge case"

## Integration

- Use `test-first-fix` once you've confirmed the cause
- Escalate to `incident-triage` if the impact is production-wide
