# Dependency Audit

## Overview

This skill covers the concrete mechanics of auditing dependency updates: which tool per ecosystem, how to read the output, and how to distinguish blocking issues from accepted risks.

## When to Use

**Always:**
- Merging a Dependabot or Renovate PR
- Adding a new direct dependency
- Bumping a major version of any dependency

**Use this ESPECIALLY when:**
- Dependencies with recent maintainer turnover
- Packages under 1M downloads/month (less community scrutiny)
- Packages that request unusual scopes (network, filesystem, env)

**Don't skip when:**
- "It's just a patch bump" — patch bumps have shipped malicious code before
- "Renovate merged it already" — Renovate doesn't audit for you

## The Process

### Phase 1: Run the audit tool

1. npm/pnpm: `npm audit --production`
2. pip: `pip-audit`
3. go: `govulncheck ./...`
4. cargo: `cargo audit`

### Phase 2: Read the diff of dependencies actually changing

1. For each bumped package: what version, what changelog?
2. For each new transitive: is the package one you recognize?

### Phase 3: Investigate each advisory

1. Is it exploitable in your usage?
2. Is there a patched version available?
3. If accepting risk: document why.

### Phase 4: Approve or block

1. Clean audit + read changelogs → approve.
2. Advisories present → block until addressed or accepted with documentation.

## Quick Reference

1. Run the ecosystem audit tool.
2. Read the diff of changed dependencies.
3. For each bumped package, read the changelog.
4. For each advisory, decide: patched, accepted, or blocked.
5. Document accepted risks in the PR description.
6. Approve only when audit is clean and diff is understood.

## Common Mistakes

- Auditing only direct dependencies and not transitive ones
- Skimming `npm audit` output and missing High-severity items
- Trusting a green CI as evidence the update is safe
- Not reading the changelog of the bumped version

## Example Workflow

### Scenario

Dependabot opens a PR bumping `lodash` from 4.17.20 to 4.17.21 and adds a new transitive `event-stream@3.3.6`.

### Applying this skill

1. Run `npm audit`. Reports 0 vulnerabilities.
2. Read the diff of dependencies. lodash bump is a small patch — read the changelog, confirms it's a prototype-pollution fix.
3. New transitive: `event-stream@3.3.6`. That's the version historically compromised in the flatmap-stream incident. Refuse to merge until the parent dependency that introduced it (`some-charting-lib`) is either updated to drop it, or replaced.

Note: without step 3, this PR would have introduced a known-bad transitive.

## Commands

```bash
# Per ecosystem
npm audit --production       # Node
pip-audit                    # Python
govulncheck ./...            # Go
cargo audit                  # Rust
bundle audit                 # Ruby

# Diff the lockfile in a PR to see what actually changed
git diff origin/main -- package-lock.json | head -100

# Read the changelog for a bumped package
npm view lodash@4.17.21 --json | jq '.description, .homepage'
```

## Red Flags

**STOP if you catch yourself doing any of these:**

- Audit tool reports CVEs and the PR was opened anyway
- Package's git repo doesn't match the registry entry
- Recent version bump with no changelog entry
- Author account created in the last 30 days for a critical dependency
- Postinstall script that fetches from a URL

## Integration

- Combine with `secrets-check` before every push
- Escalate to `incident-triage` if audit surfaces active exploitation
