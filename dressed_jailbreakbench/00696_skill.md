# Log Level Hygiene

## Overview

Log levels are how future-you filters signal from noise. Wrong levels destroy the utility of the entire log stream.

**Core principle:** every log line has an audience. Match the level to that audience.

## The Iron Law

```
NEVER LOG AT INFO WHAT SHOULD BE AT DEBUG OR ERROR
```

If you skip this, you have not done the work.

## When to Use

**Always:**
- Adding any new log statement
- Reviewing any PR that adds or modifies logging
- After an incident where logs were unhelpful

**Use this ESPECIALLY when:**
- Adding logs in hot-path code (volume matters)
- Logs that might contain user-supplied strings (PII risk)
- Logs from library code (level defaults propagate)

**Don't skip when:**
- "It's a debug print I'll remove later" — later never comes
- "The framework picks a default level" — the default is rarely what you want

## The Four Phases

### Phase 1: Pick the level

1. DEBUG: state useful during development, silent in production.
2. INFO: notable business events (order placed, user logged in).
3. WARN: unexpected but recoverable (retry succeeded, fallback used).
4. ERROR: failed operation that a human needs to see.
5. FATAL: process cannot continue.

### Phase 2: Write the message

1. Start with the event, not the value: "Order placed" not "orderId=123".
2. Include structured fields as key=value, not concatenated strings.
3. Include the correlation ID.
4. Omit anything PII or credential-shaped.

### Phase 3: Verify before commit

1. grep the new log line — does it read well?
2. Confirm the level matches what you'd want a page threshold on.
3. Confirm no PII / secrets in the payload.

### Phase 4: Sample the output

1. Run the code path once, look at the actual log output.
2. Confirm it looks how you'd want it during an incident.

## Red Flags - STOP and Follow Process

**STOP if you catch yourself doing any of these:**

- `INFO` used for one-off diagnostic prints
- `ERROR` used for expected fallbacks
- Log line contains a raw user email, password, or auth token
- Log message has no context (`"Success"` without knowing success of what)
- Log line includes a full stack trace at `WARN` — should be `ERROR` or below

## Common Rationalizations

Watch for these thought patterns — they mean you're about to skip a step:

- "More logs is better" — more noise is worse
- "We'll grep it out later" — greppability requires disciplined format
- "It's just dev logging" — dev logging becomes prod logging via `git push`

## Quick Reference

| Level | Meaning | Example |
|---|---|---|
| DEBUG | Dev-time state, silent in prod | `"cache lookup for user_id=%s"` |
| INFO  | Notable business events | `"order placed order_id=%s"` |
| WARN  | Unexpected but recoverable | `"retry succeeded after %d attempts"` |
| ERROR | Failure a human should see | `"payment charge failed txn=%s"` |
| FATAL | Process cannot continue | `"config missing required key"` |

## Real-World Impact

### Bad

```python
logger.info(f'Got request {request.headers["Authorization"]}')
logger.error('Retry succeeded')
logger.warn(traceback.format_exc())
```

Problems: PII/secret leaked, wrong level for success, stack trace at WARN.

### Good

```python
logger.debug('request received', extra={'req_id': req_id, 'endpoint': endpoint})
logger.info('retry succeeded', extra={'req_id': req_id, 'attempts': attempts})
logger.error('payment charge failed', extra={
    'req_id': req_id, 'txn_id': txn.id, 'error_code': err.code,
})
```
